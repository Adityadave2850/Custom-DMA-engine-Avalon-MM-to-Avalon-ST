# Streaming DMA IP — Portable Avalon-MM / Avalon-ST Core

A small, self-contained FPGA IP block that reads a stream of 32-bit words out
of memory over an **Avalon-MM** master interface and streams them out one
byte at a time over an **Avalon-ST** source/sink chain onto an LED output.

This repository started life as a Quartus/Platform-Designer bring-up project
with a stubbed-out DMA engine and a missing sink module. It has been rebuilt
here into a **standard, portable, verified IP core** that drops into any
Verilog project on any board/toolchain, with no dependency on Quartus
Platform Designer (Qsys) system files.

- ✅ Plain, synthesizable Verilog-2001 — no vendor IP, no generated `.qsys` system
- ✅ Real, protocol-correct Avalon-MM and Avalon-ST handshaking (waitrequest, readdatavalid, valid/ready)
- ✅ Self-checking testbenches with a data-integrity scoreboard
- ✅ GTKWave-ready waveform dumps with a pre-built signal layout

## Background — what was broken in the original project

The original project (`avalon_producer.v`, `avalon_test.v`, `dma_engine.v`)
was a Quartus bring-up test, and had three problems that made it neither
correct nor portable:

| File | Problem |
|---|---|
| `dma_engine.v` | The FSM had `// BYPASS` comments and **never actually checked `amm_waitrequest` or `amm_readdatavalid`**. It asserted and deasserted `amm_read` within the same clock edge, so a real memory slave would never even see the request pulse. On top of that, it streamed the *read address* instead of *real memory data* — it never actually moved data from memory to the output stream. |
| `avalon_test.v` | Instantiated `mem_system`, a component generated by Quartus **Platform Designer (Qsys)**. That system file only exists inside one specific Quartus project database — it isn't portable RTL, can't be simulated with a plain Verilog simulator, and can't be dropped into another board's project. |
| — | `avalon_test.v` also instantiated `avalon_consumer`, a module that **did not exist anywhere in the project**. The design could not elaborate at all. |
| `avalon_producer.v` | This one was actually fine — a simple, self-consistent free-running Avalon-ST source. Kept as-is (comments only cleaned up). |

Every one of these is fixed in this repository (see [Module reference](#module-reference)
for the exact fix in each file).

## Architecture

```
                    ┌────────────────────────── streaming_dma_ip.v ───────────────────────────┐
                    │                                                                         │
                    │   avalon_onchip_mem.v          Avalon-MM           dma_engine.v         │
                    │   ┌──────────────────┐    ◄──────────────────►   ┌──────────────────┐   │
                    │   │  Avalon-MM SLAVE │    address/read/          │ Avalon-MM MASTER │   |
                    │   │  (block RAM,     │    readdata/              │  (read only)     │   │
                    │   │   replaces Qsys  │    readdatavalid/         │       +          │   │
                    │   │   mem_system)    │    waitrequest            │ Avalon-ST SOURCE │   │
                    │   └──────────────────┘                           └────────┬─────────┘   │
                    │                                                           │ Avalon-ST   │
                    │                                                           │ data/valid/ │
                    │                                                           │ ready       │
                    │                                                           ▼             │
                    │                                                 avalon_consumer.v       │
                    │                                                 (Avalon-ST SINK, drives │
                    │                                                  led_output)            │
                    │                                                                         │
                    └─────────────────────────────────────────────────────────────────────────┘
                                                             │
                                                        led_output[7:0]
```

**Data flow:** `dma_engine` issues sequential 32-bit reads to
`avalon_onchip_mem` starting at address `0`, wrapping back to `0` once it
reaches the top of the configured memory depth. For every word it reads back,
it pushes the low byte out over its Avalon-ST source port. `avalon_consumer`
accepts each byte and latches it onto `led_output`, so you can watch the
memory contents "stream past" on the LEDs (or in the waveform, in
simulation).

An independent, simpler path is also included: `avalon_producer.v` is a
free-running Avalon-ST source (a plain up-counter, 0→255→0→…) that can be
wired directly into `avalon_consumer.v` without any DMA/memory involved —
useful as a minimal reference for the Avalon-ST handshake on its own.

## Protocol primer

If you're not already familiar with Avalon interfaces, here's the short
version of what this IP implements.

### Avalon-MM (Memory-Mapped) — used between `dma_engine` and `avalon_onchip_mem`

A simple address/data bus with back-pressure:

| Signal | Direction (master→slave unless noted) | Meaning |
|---|---|---|
| `address` | → | Byte address of the word being requested |
| `read` | → | "I am requesting a read this cycle" |
| `waitrequest` | ← (slave→master) | "Not yet — keep `read`/`address` held, I'm not ready" |
| `readdata` | ← | The data word, valid only when `readdatavalid` is high |
| `readdatavalid` | ← | "The data on `readdata` right now is valid" |

**Handshake rule:** a request is *accepted* on the first cycle where both
`read` and `!waitrequest` are true. The master must keep `address`/`read`
stable until that happens. Some cycles later (the slave's read latency), the
slave returns the data with `readdatavalid` pulsed for exactly one cycle.

### Avalon-ST (Streaming) — used between `dma_engine`/`avalon_producer` and `avalon_consumer`

A simpler, unidirectional streaming handshake:

| Signal | Direction (source→sink unless noted) | Meaning |
|---|---|---|
| `data` | → | The byte being offered |
| `valid` | → | "This data is real, take it if you can" |
| `ready` | ← (sink→source) | "I can accept data this cycle" |

**Handshake rule:** a transfer happens on any cycle where both `valid` and
`ready` are high simultaneously. If `ready` is low, the source must keep
`data`/`valid` stable until the sink is ready.

Both protocols are why this design is interesting to verify: a source (or
master) is not allowed to assume the other side is always ready, and this
repo's testbench deliberately exercises the "not ready" case on *both*
interfaces so you can see real back-pressure at work in the waveforms.

## Module reference

### `rtl/dma_engine.v` — Avalon-MM read master + Avalon-ST source

```verilog
module dma_engine #(
    parameter ADDR_WIDTH = 8,     // width of amm_address
    parameter ADDR_MAX   = 255    // last valid BYTE address, then wrap to 0
)(
    input  wire                    clk,
    input  wire                    reset_n,
    output reg  [ADDR_WIDTH-1:0]   amm_address,
    output reg                     amm_read,
    input  wire [31:0]             amm_readdata,
    input  wire                    amm_readdatavalid,
    input  wire                    amm_waitrequest,
    output reg  [7:0]              aso_data,
    output reg                     aso_valid,
    input  wire                    aso_ready
);
```

A 4-state FSM (`IDLE → READ → WAIT → WRITE → READ → …`):

1. **IDLE** — waits for the downstream sink to be ready before issuing the
   first request.
2. **READ** — drives `amm_address`/`amm_read` and holds them until the slave
   accepts the request (`amm_read && !amm_waitrequest`).
   > **The fix that matters most is here.** `amm_read` is a *registered*
   > output — it only becomes visible to the slave one cycle after it's
   > assigned. The original code checked `amm_waitrequest` in the very same
   > cycle it first raised `amm_read`, so it always saw the *previous*
   > (low) `waitrequest` value and immediately cleared `amm_read` again —
   > the slave never saw the request pulse at all. The fix is the standard
   > idiom: only treat the request as accepted once `amm_read` was
   > *already* high on entry to this check.
3. **WAIT** — waits for `amm_readdatavalid` before trusting `amm_readdata`.
4. **WRITE** — presents the real memory data's low byte on `aso_data`, holds
   `aso_valid` until the sink accepts it, then advances (and wraps) the read
   address.

### `rtl/avalon_onchip_mem.v` — Avalon-MM slave memory model (new)

```verilog
module avalon_onchip_mem #(
    parameter ADDR_WIDTH   = 8,
    parameter DATA_WIDTH   = 32,
    parameter MEM_WORDS    = 64,
    parameter LATENCY      = 2,   // cycles from accepted request to readdatavalid
    parameter STALL_PERIOD = 5    // assert waitrequest for 1 cycle every N reads (0 = never)
)( ... );
```

Plain inferred block-RAM, pre-loaded at elaboration time with a predictable
pattern (`readdata[7:0] == (word_index*2 + 1) & 0xFF`) so a testbench can
compute the expected output purely from the address, without needing to
inspect memory contents directly. Includes a configurable stall generator so
the master's `waitrequest` handling is genuinely exercised in simulation,
not just assumed to always be zero.

This module is the direct, portable replacement for the Quartus
Platform-Designer-generated `mem_system` the original top level depended on.

### `rtl/avalon_consumer.v` — Avalon-ST sink (new)

```verilog
module avalon_consumer #(
    parameter STALL_PERIOD = 0   // assert !ready for 1 cycle every N transfers (0 = always ready)
)( ... );
```

Accepts a byte per valid/ready handshake and latches it onto `led_output`.
Also exposes a free-running `xfer_count` debug output and an optional
backpressure generator (`STALL_PERIOD`) to exercise the upstream source's
`valid`-held-while-`!ready` behavior.

### `rtl/avalon_producer.v` — standalone free-running source (kept)

Unmodified logic from the original project: a simple up-counter offered on
an Avalon-ST source, useful on its own without any DMA/memory involved.

### `rtl/streaming_dma_ip.v` — top-level portable IP core (new)

Wires `avalon_onchip_mem` + `dma_engine` + `avalon_consumer` together behind
a clean, board-agnostic port list: `clk`, `reset_n`, `led_output`, plus a set
of `dbg_*` monitor ports (address, read, waitrequest, readdatavalid, stream
data/valid/ready, transfer count) purely so every protocol signal is easy to
find and probe in a waveform viewer. This is the file you'd instantiate in
your own project.

### `rtl/avalon_test.v` — board-level pin wrapper (rewritten)

Now just a thin mapping of one board's pin names (`CLOCK_50` / `KEY[0]` /
`LEDG`, Terasic-DE-series style) onto `streaming_dma_ip`. No `mem_system`,
no Qsys — this is the *only* file that should need editing to move the IP to
a different board.

## Running the simulations

### Quickest path — the provided script

```bash
cd sim
chmod +x run_sims.sh
./run_sims.sh
```

This builds and runs **both** testbenches and prints a `PASS`/`FAIL` summary
for each, e.g.:

```
TEST SUMMARY
   transfers checked : 357
   mismatches        : 0
   RESULT            : PASS
```

### Manual, step-by-step

**Main DMA pipeline testbench** (memory → DMA engine → stream → sink):

```bash
cd sim
iverilog -g2005 -o sim_dma.out \
    ../rtl/dma_engine.v \
    ../rtl/avalon_onchip_mem.v \
    ../rtl/avalon_consumer.v \
    ../rtl/streaming_dma_ip.v \
    ../tb/tb_streaming_dma_ip.v

vvp sim_dma.out
```

**Standalone producer → consumer testbench:**

```bash
iverilog -g2005 -o sim_pc.out \
    ../rtl/avalon_producer.v \
    ../rtl/avalon_consumer.v \
    ../tb/tb_producer_consumer.v

vvp sim_pc.out
```

Both `vvp` runs regenerate the corresponding `.vcd` file in `sim/`, so you
can re-run this any time you change the RTL.

## Reading the waveforms in GTKWave

```bash
cd sim
gtkwave streaming_dma_ip.vcd streaming_dma_ip.gtkw   # main test, signals pre-grouped
gtkwave producer_consumer.vcd                         # secondary test (no saved layout)
```

`streaming_dma_ip.gtkw` groups the signals into the three things worth
watching, top to bottom:

1. **Avalon-MM master ↔ slave** — `dbg_amm_address`, `dbg_amm_read`,
   `dbg_amm_waitrequest`, `dbg_amm_readdata`, `dbg_amm_readdatavalid`.
   Watch `amm_read` stay asserted across any stall cycles until
   `amm_waitrequest` drops, then `amm_readdatavalid` pulse `LATENCY` cycles
   later with the correct word on `amm_readdata`.
2. **Avalon-ST source ↔ sink** — `dbg_stream_data`, `dbg_stream_valid`,
   `dbg_stream_ready`. Watch `valid` held steady whenever `ready` is low
   (sink backpressure), and a transfer only actually happening when both are
   high together.
3. **Result** — `led_output` (the byte that actually reached the "board")
   and `dbg_xfer_count` (a running transfer counter). `led_output` should
   step through the memory's known pattern, and `dbg_xfer_count` climbs
   steadily and resets to a repeating cycle at each address wrap.

If you'd rather explore manually: every signal in the design hierarchy is in
the VCD (the testbench calls `$dumpvars(0, ...)` on itself), so you can drag
in anything from the SST/hierarchy pane on the left of GTKWave, including
internal signals like `dut.u_dma.state` or `dut.u_mem.mem` if you want to go
deeper.

## Porting to a real board

Only `rtl/avalon_test.v` is board-specific. To move this IP to a different
board:

1. Copy `avalon_test.v` and rename its top-level ports to your board's
   actual pin names (system clock, reset button/switch, LEDs).
2. Keep the `streaming_dma_ip` instantiation and its parameters unchanged
   (or adjust `MEM_WORDS`/`MEM_LATENCY`/etc. to taste — see parameter table
   below).
3. Add every file under `rtl/` to your synthesis project, with your renamed
   wrapper set as the top-level module.

No Qsys/Platform Designer system file is required anywhere in this flow —
just plain RTL.

### `streaming_dma_ip` parameters

| Parameter | Default | Meaning |
|---|---|---|
| `ADDR_WIDTH` | 8 | Avalon-MM byte address width |
| `MEM_WORDS` | 64 | Internal memory depth, in 32-bit words |
| `MEM_LATENCY` | 2 | Memory read latency, in cycles |
| `MEM_STALL_PERIOD` | 5 | Memory `waitrequest` stall period (`0` = never stall) |
| `CONSUMER_STALL_PERIOD` | 0 | Sink backpressure period (`0` = always ready) |

## Known limitations / possible extensions

- The Avalon-MM master supports a single outstanding read transaction (no
  burst/pipelining) — sufficient for this IP's purpose, but a throughput
  upgrade would add burst support.
- `avalon_onchip_mem.v` is read-only; there's no write path modeled.
- The board-level LED output is a simple byte mirror; a real product would
  likely add a FIFO or a wider downstream consumer instead of `led_output`.

Pull requests / issues welcome if you extend this for your own board or use
case.
